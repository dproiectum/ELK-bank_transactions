# Log Fields

This directory receives the raw log files generated by `generator/generate.py`.
Generated `.log` and `.csv` files are ignored by Git; this document explains
their structure.

## Files

```text
transactions.log  payment transaction events, key-value text format
auth.log          authentication events, JSON format
atm.csv           ATM events, CSV format
```

The generator intentionally creates about 2% malformed lines. Logstash routes
those lines to `bank-deadletter-*` instead of silently dropping them.

## transactions.log

Example:

```text
ts=2026-07-26T00:00:00Z ev=txn id=t-8100000 amount=238.64 currency=EUR country=ES card_present=false merchant=m-0348 status=approved
```

| Field | Meaning | Example |
| --- | --- | --- |
| `ts` | Event timestamp in UTC. In batch mode, it starts on `2026-07-26`. | `2026-07-26T00:00:00Z` |
| `ev` | Event type. For this file, it is always `txn` when the line is valid. | `txn` |
| `id` | Transaction identifier. | `t-8100000` |
| `amount` | Transaction amount. | `238.64` |
| `currency` | Transaction currency. | `EUR`, `USD`, `GBP` |
| `country` | Country where the transaction is associated. | `FR`, `US`, `BE` |
| `card_present` | Whether the physical card was present. | `true`, `false` |
| `merchant` | Merchant identifier. | `m-0348` |
| `status` | Transaction result. | `approved`, `declined` |
| `reason` | Decline reason. Present only when the transaction is declined. | `suspected_fraud` |

Fraud scenario: during the anomaly window, the generator creates a burst of
declined card-not-present transactions from the US with reason
`suspected_fraud`.

## auth.log

Example:

```json
{"ts": "2026-07-26T00:00:00Z", "event": "auth", "user": "u-12345", "channel": "web", "result": "failure", "ip": "181.214.205.10"}
```

| Field | Meaning | Example |
| --- | --- | --- |
| `ts` | Authentication event timestamp in UTC. | `2026-07-26T00:00:00Z` |
| `event` | Event type. For this file, it is `auth` when valid. | `auth` |
| `user` | User identifier. | `u-12345` |
| `channel` | Authentication channel. | `mobile`, `web`, `branch` |
| `result` | Authentication result. | `success`, `failure` |
| `ip` | Client IP address. Logstash enriches this field with GeoIP data. | `181.214.205.10` |

Fraud scenario: the suspicious authentication failures are concentrated on the
`web` channel and IPs in the `181.214.200.x` to `181.214.210.x` range.

## atm.csv

Header:

```csv
ts,atm_id,city,op,amount,result
```

Example:

```csv
2026-07-26T00:00:00Z,atm-0021,Paris,withdrawal,100.00,ok
```

| Field | Meaning | Example |
| --- | --- | --- |
| `ts` | ATM event timestamp in UTC. | `2026-07-26T00:00:00Z` |
| `atm_id` | ATM identifier. | `atm-0021` |
| `city` | City where the ATM is located. | `Paris`, `Lille`, `Lyon` |
| `op` | ATM operation. | `withdrawal`, `deposit`, `balance` |
| `amount` | Cash amount. Balance checks use `0.00`. | `100.00` |
| `result` | ATM operation result. | `ok`, `timeout`, `out_of_cash` |

The CSV header is also read by Logstash and sent to `bank-deadletter-*` with
`deadletter_reason = csv_header`. This keeps the line-count audit explicit.

## After Logstash Parsing

Logstash normalizes valid events before indexing:

| Raw field | Elasticsearch field |
| --- | --- |
| `ts` | `@timestamp` |
| transaction `ev` | `event_type` |
| transaction `id` | `transaction_id` |
| auth `event` | `event_type` |
| auth `user` | `user_id` |
| auth `ip` | `client_ip` |

It also adds `source_type` with one of these values:

```text
transactions
auth
atm
```
